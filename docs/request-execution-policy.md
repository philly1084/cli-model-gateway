# Request deadline, fallback and cancellation policy

Chat completions (including message aliases) and Responses validate gateway_policy: operationId, allowFallback, maxAttempts (1-8), maxLatencyMs (1-600000), optional maxEvidenceAgeMs. Unknown or malformed policy fields are rejected before provider invocation. Explicit model IDs and configured provider/runtime pins are not changed. Requests without gateway_policy retain configured routing/default provider deadlines, while HTTP disconnect now reaches both buffered and native-streaming transports.

A trusted HTTP arrival timestamp defines one absolute deadline. Validation/queue time, CLI preparation, app-server initialization and generation consume this same budget; fallback attempts do not reset it. The registry enforces no-fallback and attempt limits before selecting/invoking another provider. Deadline or client cancellation blocks subsequent attempts, observes late promise rejections, and never turns a late response into success. HTTP transport failures with uncertain delivery also stop fallback. A native stream must reach a terminal done event to count as success.

CLI request processes receive their own POSIX process group. Cancellation requests SIGTERM for that owned group, escalates to SIGKILL after one second and bounds local cleanup observation. It never signals a preexisting/shared group. HTTP providers receive the combined caller/deadline signal, including buffered JSON and the existing Kimi API path. Provider JSON excludes internal execution objects and callbacks. Windows fixtures only confirm direct-child exit, not descendant cleanup; production's Linux group checks are separately exercised in hosted CI.

Existing structured logs receive correlated attempt, local dispatch, terminal and local-cleanup metadata. Fields are IDs, selected/requested model, attempt count, timestamp and outcome; prompts, credentials, stdout/stderr bodies and tool arguments are excluded. Validation logs no longer include request bodies. Terminal is emitted once per gateway request. A local dispatch event is explicitly not a provider receipt. Cancellation and incomplete/failed delivery remain providerOutcome=unknown after dispatch; even confirmed local process-group absence does not prove cancellation or billing cessation at the remote provider. Uncooperative providers may finish after the response deadline; they are never automatically retried by this request.

These are log receipts, not a new durable replay/idempotency store. operationId correlates events but does not authorize retry; HTTP retries can create new requests. No new endpoint, credential, permission, firewall rule, package, provider configuration, model default or Kimi pin is introduced. maxEvidenceAgeMs is accepted for existing client compatibility; this patch does not implement compatibility-evidence freshness or advertise routing_policy_version=1. No claim of the broader evidence-routing contract is made.

Offline tests exercise real Chat/Responses HTTP disconnects with synthetic providers, cancellation during startup, expired queue budgets, fallback suppression/caps, incomplete streams, late/uncertain outcomes, an actual disposable CLI process and buffered provider fetch cancellation. Existing compiled/protocol/release suites run unchanged. No live provider request is part of this validation.

Deployment requires exact-head hosted CI and the existing signed digest-pinned main-release workflow after authorized merge. Preserve the live provider ConfigMap, CLI/Kimi/bootstrap identities, mounts, service account, credentials and ingress. Do not apply the repository Kubernetes bundle. Existing automatic startup/periodic benchmark settings can invoke models during rollout; explicit suppression or a separately approved inference budget is a deployment decision, not a code default change.
